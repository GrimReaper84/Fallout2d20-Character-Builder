# Legacy app analysis

You reconstruct what the legacy app **actually does** for a feature and classify it against the
rulebooks. The result is the knowledge base for `java-analyzer` and `javafx-planner`. Nothing is
translated, refactored or planned here.

Why the book check happens already here: the legacy app was generated by an AI. It contains wrong
values, invented rules and unverified supplement content, and its README and comments overstate what
was checked. If the analysis separates code behavior from book rules cleanly, the planner no longer
has to guess what is binding.

**Read first:** `.claude/skills/_shared/project-rules.md`, especially sections 3 (paths), 4 (book
check) and 5 (scope).

## Inputs

- Feature name or the user's question.
- Legacy app under `/home/luca/Documents/Fallout 2d20/v0.4.5/`:
  - `src/model/` – `Character.ts` (save model), `migrate.ts` (v1 → v2 migration)
  - `src/rules/` – `creation.ts`, `perks.ts`, `derived.ts`, `armor.ts`
  - `src/data/` – catalogs as TS objects (`coreOrigins`, `corePerks`, `perks`, `coreEquipment`,
    `winterOrigins`, `winterEquipment`, `weapons`, `skills`, `progression`, `attachments`, ...)
  - `src/ui/app.ts` (≈1000 lines, `@ts-nocheck`, much logic inline), `sheet.ts`
  - `tests/` – rule and smoke tests, `README.md` (feature claims)
  - Older versions (`v0.4.2`, `v0.4.3`, `fallout-character-manager` with the original `index.html`)
    only when the history of a behavior matters.
- Legacy save example: `/home/luca/Documents/Fallout 2d20/Characters/JC.json`.
- Rulebooks: `docs/rulebooks/<book>.txt` / `_layout.txt` (+ PDF for page images).

## Procedure

1. **Find the entry points:** UI action in `app.ts` (event handler, inline `onclick`) → functions in
   `rules/` → data in `data/`. Grep for names, read the relevant sections. Do not read `app.ts` in one
   go if only a part is relevant.
2. **Describe actual behavior**, not presumed intent. If code looks wrong, document the observed
   behavior and mark it as a risk. Do not silently correct it.
3. **Capture mode differences:** creation (budgets, validation) vs. level-up/progression vs. free
   edit. Where does each check happen, and where is it skipped?
4. **Capture the save format:** which fields of `Character.ts`/`JC.json` belong to the feature, how
   `migrate.ts` treats them, which values are stored although they could be derived. This feeds the
   legacy importer.
5. **Measure the data:** how many catalog entries, from which book (comments, `source`-like fields,
   file names such as `core*`/`winter*`), how many of them verified per README.
6. **Check every rule and value against the books.** Outcomes: confirmed (book + page + paraphrase),
   contradicted (the book says otherwise), legacy only (no book evidence → invention, house rule or
   other book), unclear. With 0 hits, try spelling variants and the other two books before concluding
   "no evidence".
7. **Write the file** `docs/analyses/<feature>_legacy_analysis.md`, then stop and report the main
   findings, legacy-vs-book conflicts and open questions briefly to the user (in German).

For large scope (many modules, >1,500 relevant lines) the analysis can be handed to a fork agent to
keep the main context free.

## Classifications

| Label | Meaning |
|---|---|
| `Confirmed (code+book)` | Present in the code and confirmed by the book, strongest level |
| `Confirmed (code)` | Present in the code, book reference missing or not checked |
| `Contradicted` | The book says something else (give both values) |
| `Probable` | plausible, not fully provable |
| `Unclear` | context missing or ambiguous |
| `Legacy debt` | technically questionable (logic in UI, stored derived values, free text instead of structure), do not port 1:1 |
| `Do not port without check` | possible bug, invention, or unverified supplement content |

Always cite concretely: `src/rules/perks.ts:12-40`, `CRB p. 59`.

## Watch out for in this code

- Rules split between `rules/*.ts` and inline logic in `app.ts`; the UI sometimes recomputes or
  bypasses checks.
- Requirements as **free-text strings** (`"END 7, Level 1+, not a robot"`) parsed at runtime.
- Values stored in the save although derivable (`derived`, `vitals.currentHP` vs. max HP).
- Free-text inventory (`equipment: string`) and weapon objects with string fields (`dmg: "3"`).
- Name-based special cases (`Mister Handy`, `Intense Training`, `Gifted`, origin-specific flags such as
  `noPincer`).
- Hidden-but-kept data (e.g. Generation 2 Synth readable in old saves, hidden for new characters).
- GM override switches that disable validation.

## Output: `docs/analyses/<feature>_legacy_analysis.md`

```markdown
# Legacy analysis: <feature>

> Scope, date, what was deliberately not analyzed.

## Overview
(relevant files as table: file:lines | role | classification)

## Extracted rules
### Rule: <name>
**Status:** <classification>
**Description:** If …, then …
**Source:** code location(s); book page + paraphrase, or "no book evidence (searched: …)"
**Migration relevance:** …
**Test scenarios:** …

## Data and save format
(fields as table: field | type | meaning | stored or derived | importer relevance)

## Open questions
(per question: why relevant, observation so far, recommended next search)

# Hand-off to javafx-planner
- Confirmed behavior / must be ported
- Rules table: rule | status | source | priority
- Conflicts legacy ↔ book
- Legacy only / other books (proposal: defer)
- Legacy debt that should not be ported
- Legacy save fields and how the importer must map them
- Derived test scenarios (book examples first)
- Risks for the rebuild
```

The hand-off at the end is what the planner actually needs. It must be understandable without the
rest of the file.
